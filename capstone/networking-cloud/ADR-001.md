# ADR-001: Keep the app serving through a node failure, then autoscale Flask

- **Status:** Proposed
- **Date:** 2026-11-19
- **Track:** Networking and Cloud Infrastructure
- **Team:** Team 1 (cluster `team1`, Kubernetes port 8091, Prometheus port 9091)

## Context

Harborlight expects about 3x more statustracker traffic, and the Operations Support Desk must keep working through a bad afternoon. The platform has to add capacity on its own and keep serving while a node is down, on the existing shared VM, with no new paid services, and within a 768Mi memory budget beyond today's baseline.

Our cluster today (from `infrastructure/flask.tf` and `manifests/`):

| Tier | Replicas today | Requests / limits | Probes | Notes |
| --- | --- | --- | --- | --- |
| Flask | 3 (fixed, no autoscaler) | CPU 100m / 500m, memory 128Mi / 256Mi | Liveness only (`curl /health`) | No rule spreads its pods across nodes |
| nginx | 1, `Recreate` strategy | None set | Liveness only | Single point of failure in front of Flask |
| PostgreSQL | 1 | Not changed | Liveness (`pg_isready`) | The track does not allow scaling the database |

NetworkPolicies already in place: `default-deny-ingress`, `allow-ingress-to-nginx`, `allow-nginx-to-flask`, `allow-flask-to-postgres`.

Two problems follow. If the node that holds the only nginx pod stops, every request fails until Kubernetes reschedules it. If load triples, nothing adds Flask capacity.

## Decision

We will take the track README's **Approach B (survive the failure) first, then Approach A (autoscale)**, and document the network path as we go (the analysis part of Approach C).

1. **Keep serving when a node stops (criteria 2 and 3)**
   - Run **nginx at 2 replicas** and switch it from `Recreate` to `RollingUpdate`. Give it memory and CPU requests and limits (memory 32Mi / 64Mi, CPU 50m request).
   - Spread Flask and nginx pods across nodes with a `topologySpreadConstraints` rule on `kubernetes.io/hostname` (`maxSkew: 1`).
   - Add a **readiness probe** on `/health` to Flask and to nginx, so a pod that stops answering leaves the Service quickly.
   - Add a **PodDisruptionBudget** with `minAvailable: 1` for Flask and for nginx. We will record honestly that a PDB only limits voluntary disruptions (a drain), not a `docker stop`.
2. **Autoscale Flask (criterion 1)**
   - Add a **HorizontalPodAutoscaler** for Flask: `minReplicas: 2`, `maxReplicas: 4` (the track's cap), target 60% of the 100m CPU request.
   - Drive it with a **stepped k6 test using an arrival-rate executor** (1x, 2x, then 3x our baseline request rate, each step held a few minutes), and save `kubectl get hpa -w` output to `evidence/hpa-over-time.txt`.
3. **Prove it with a node drill (criterion 2)**
   - Stop **one of our own agent nodes** (`k3d-team1-agent-0` or `-agent-1`) for at least 3 minutes while k6 sends traffic to `http://localhost:8091/health` with the threshold `http_req_failed < 0.01`. Record exact stop and start times.
   - Before the drill, check `kubectl get pods -o wide` and pick the agent that does **not** host the database, so the drill measures the scaled tiers. We never stop the server node, the load balancer container, or any container outside `k3d-team1-*`.
4. **Trace and tighten the network (criterion 4)**
   - Trace one request from k6 to the database in `ARCHITECTURE.md`: k3d load balancer, nginx Service and pods, the `flask` Service and its DNS name, Flask pods, the `db` Service and pod, and the NetworkPolicy that allows each hop. Each hop is found with a command, not guessed.
   - Candidate policy change: `default-deny-ingress` likely also blocks Prometheus (in the `monitoring` namespace) from scraping Flask's `/metrics`. In Week 11 we will confirm that target's state; if it is blocked, we add an `allow-prometheus-to-flask` policy and test both the allowed path and a denied debug pod, before and after.
5. **How changes ship**
   - Live changes are made with `kubectl` on a branch and merged by pull request. Flask's changes are also written into `infrastructure/flask.tf` and the HPA and PDBs are described in OpenTofu marked **[PREDICT ONLY]**. We do not run `tofu` or Ansible on the shared VM.

## Memory budget (criterion 5)

Worst case beyond today's baseline, using limits:

| Addition | Calculation | Memory |
| --- | --- | --- |
| Flask scaling past today's 3 replicas | 1 extra pod at `maxReplicas: 4` x 256Mi | 256Mi |
| nginx second replica, now with a limit | 2 pods x 64Mi (counted in full, since nginx had no limit before) | 128Mi |
| One debug pod at a time (DNS and policy tests) | 1 x 64Mi | 64Mi |
| **Total** | | **448Mi of 768Mi (320Mi spare)** |

We will re-check this against `kubectl top pods -A` and `free -h` once the changes are live, and save the arithmetic in `evidence/`.

## Alternatives considered

| Option | Why we did not choose it |
| --- | --- |
| Linkerd or Cilium service mesh (named in the Canvas summary) | Not part of the track README's success criteria. Linkerd adds a control plane and a proxy container in every pod, which eats into the 768Mi budget, and each new pod needs its own allow policy under default-deny. Cilium replaces the cluster's network plugin, which means recreating the cluster and complicates the Week 14 rebuild. **We are confirming with the professor that the track README is the spec.** |
| Approach A only (autoscale, no spreading or PDBs) | Adds capacity under load but does not stop the single nginx pod from taking the whole app down during a node failure. |
| Approach C only (network analysis first) | Documents the system without changing what users feel during load or a node loss. We keep its analysis but not as the main focus. |
| Scale or replicate PostgreSQL | Not allowed by the track. A highly available database needs replication and failover decisions that are out of scope. |
| Keep Flask at a fixed 3 replicas | Survives a node loss but never grows under 3x load, and holds 768Mi of limits even when idle. |

## Consequences

- **Better:** no single nginx or Flask pod can take the app down; Flask grows with load up to a hard cap; every claim is backed by a saved evidence file.
- **Costs:** about 448Mi more memory in the worst case; more manifests to keep in sync with `flask.tf`.
- **Still true:** the database remains a single pod, so stopping the node that hosts it would still cause errors; the autoscaler reacts after load arrives, so users may see slower responses for the first minute of a spike; on the shared VM, other teams' load can affect our measurements.
